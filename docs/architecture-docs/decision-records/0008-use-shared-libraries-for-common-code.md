# ADR-0008: 使用共享库管理公共代码

**状态**: 已接受  
**日期**: 2024-01-25  
**作者**: 架构团队  
**相关ADR**: ADR-0003  
**标签**: 架构决策 | 流程决策

## 1. 决策背景和问题陈述

### 背景
在微服务架构中，多个服务需要共享通用功能：
- 统一日志记录（logger.py）
- 统一错误处理（error_handler.py）
- 统一配置管理（config.py）
- HTTP客户端（http_client.py）
- 数据模型定义（schemas/）

如果每个服务都实现这些功能，会导致：
- 代码重复
- 维护困难（修改需要在多个地方同步）
- 不一致性（不同服务实现可能不同）

### 问题陈述
- 如何管理多个服务共享的公共代码？
- 如何避免代码重复？
- 如何保证代码一致性？
- 如何管理共享库的版本？

### 约束条件
- 必须支持Python包管理
- 必须易于安装和使用
- 必须支持版本控制
- 必须不破坏现有服务

## 2. 考虑的方案

### 方案A: 共享库（shared-libs）

**描述**: 创建独立的共享库模块（shared-libs），所有服务导入使用。

**优点**:
- ✅ 代码集中管理，易于维护
- ✅ 避免代码重复
- ✅ 保证一致性（所有服务使用相同实现）
- ✅ 易于版本管理（Git标签）
- ✅ 可以独立测试和发布

**缺点**:
- ❌ 需要手动管理依赖（pip install -e）
- ❌ 共享库变更可能影响多个服务（需要协调）

### 方案B: Git Submodule

**描述**: 使用Git Submodule管理共享代码。

**优点**:
- ✅ 版本控制集成
- ✅ 可以引用特定版本

**缺点**:
- ❌ Git Submodule使用复杂
- ❌ 更新需要手动同步
- ❌ 团队协作困难

### 方案C: 每个服务独立实现

**描述**: 每个服务独立实现公共功能。

**优点**:
- ✅ 服务完全独立
- ✅ 可以针对服务优化

**缺点**:
- ❌ 代码重复严重
- ❌ 维护困难（需要在多个地方修改）
- ❌ 不一致性（不同实现）

### 方案D: 发布到PyPI

**描述**: 将共享库发布到PyPI，服务通过pip安装。

**优点**:
- ✅ 标准的包管理方式
- ✅ 版本管理清晰

**缺点**:
- ❌ 开发阶段发布和更新复杂
- ❌ 需要维护PyPI包
- ❌ 不适合快速迭代

## 3. 决策结果

### 选择的方案
**方案A**: 共享库（shared-libs）

### 决策理由
1. **代码复用**: 集中管理公共代码，避免重复
2. **一致性**: 所有服务使用相同的实现，保证一致性
3. **维护性**: 修改一处，所有服务自动受益
4. **开发效率**: 减少重复开发，提高效率
5. **灵活性**: 可以针对不同服务提供不同版本（如果需要）

### 决策标准
- **代码复用**（权重：高）- 避免重复
- **维护性**（权重：高）- 易于维护
- **一致性**（权重：高）- 保证一致性
- **开发效率**（权重：中）- 提高效率

## 4. 影响和后果

### 正面影响
- ✅ **代码复用**: 公共代码集中管理，避免重复
- ✅ **一致性**: 所有服务使用相同的日志、错误处理等
- ✅ **维护性**: 修改一处，所有服务自动更新
- ✅ **开发效率**: 减少重复开发，提高开发速度

### 负面影响
- ❌ **耦合风险**: 共享库变更可能影响多个服务
- ❌ **版本管理**: 需要管理共享库版本

### 缓解措施
- **耦合风险**: 建立共享库变更流程，重大变更需要通知所有服务
- **版本管理**: 使用语义化版本，重大变更升级主版本号

### 技术债务
- 共享库版本管理需要完善（计划在Q2完成）
- 共享库测试覆盖率需要提升（计划在Q2完成）
