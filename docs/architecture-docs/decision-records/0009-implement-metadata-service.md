# ADR-0009: 实现元数据管理服务

## 状态

已接受

## 背景

随着平台规模的扩大和服务的增多，需要一个统一的元数据管理服务来：
1. 集中管理所有数据资产、AI模型、业务实体、工作流的元数据
2. 追踪数据之间的血缘关系，支持数据治理
3. 监控数据质量，确保数据可靠性
4. 提供元数据搜索和发现能力

## 决策

实现一个独立的元数据管理服务（metadata-service），提供以下能力：

### 核心功能

1. **元数据管理**
   - 数据资产元数据（schema、质量指标、业务信息）
   - AI模型元数据（训练配置、性能指标、部署信息）
   - 业务实体元数据（数据字典、业务规则）
   - 工作流元数据（定义、执行统计、依赖关系）

2. **数据血缘追踪**
   - 自动追踪MCP工具执行时的数据流
   - 自动追踪工作流执行时的节点间数据流
   - 自动追踪知识处理流程
   - 自动追踪模型推理过程
   - 支持血缘图谱查询和可视化

3. **元数据自动采集**
   - 服务启动时自动注册基础元数据
   - 数据变更时自动更新元数据版本
   - 工具执行时自动收集使用统计
   - 工作流运行时自动收集执行指标
   - 用户交互时收集访问模式

4. **数据质量管理**
   - 质量指标管理（完整性、准确性、一致性、及时性、有效性、唯一性）
   - 质量评分计算
   - 质量等级评估
   - 质量问题识别和告警

5. **元数据搜索**
   - 全局元数据搜索
   - 标签搜索
   - 热门标签统计

### 技术选型

- **框架**: FastAPI（与其他服务保持一致）
- **数据库**: PostgreSQL（通过共享database模块）
- **ORM**: SQLAlchemy 2.0
- **数据验证**: Pydantic v2
- **HTTP客户端**: httpx（用于采集器）

### 服务端口

- **端口**: 8005
- **服务名称**: metadata-service

### 架构设计

1. **采集器模式**
   - 使用采集器（Collector）模式从各个服务采集元数据
   - 支持多种采集时机（启动、变更、执行、交互）
   - 采集器独立于主业务流程，异步执行

2. **血缘追踪**
   - 使用LineageCollector统一追踪血缘关系
   - 自动从输入输出数据中提取数据源和目标
   - 支持多种血缘类型（数据流、依赖关系、转换关系）

3. **数据模型**
   - 使用共享的database模块定义数据模型
   - 使用shared_libs定义跨服务的Pydantic模型
   - 支持数据质量指标模型（DataQualityMetrics）

## 后果

### 优点

1. **集中管理**: 所有元数据集中在一个服务中，便于管理和查询
2. **自动化**: 元数据采集和血缘追踪自动化，减少人工维护成本
3. **数据治理**: 支持数据血缘和质量监控，提升数据治理能力
4. **可扩展**: 采集器模式易于扩展新的采集源和采集时机
5. **标准化**: 统一的元数据模型，便于跨服务使用

### 缺点

1. **依赖增加**: 其他服务需要依赖metadata-service
2. **性能影响**: 采集操作可能对主业务有轻微性能影响（已通过异步执行缓解）
3. **数据一致性**: 采集的数据可能与实际数据有短暂延迟

### 风险

1. **服务可用性**: metadata-service不可用会影响元数据采集，但不影响主业务
2. **数据量增长**: 随着元数据增多，需要优化查询性能
3. **血缘追踪准确性**: 自动提取的数据源和目标可能不准确，需要人工验证

### 缓解措施

1. **异步执行**: 所有采集操作异步执行，不阻塞主业务
2. **错误处理**: 采集失败不影响主业务，只记录警告日志
3. **性能优化**: 使用索引、缓存等技术优化查询性能
4. **人工验证**: 提供血缘关系验证和修正功能
